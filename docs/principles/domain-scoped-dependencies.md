# domain-scoped-dependencies — A block may not depend on another domain's block

**Rule:** Every crate, engine command module and `ui/src` domain is substrate, a block, or the shell. Substrate is always on and may depend only on substrate. A block may depend on substrate and on its own domain, never on another domain's block. Only the shell may know every block. Two features that need the same behaviour write it twice rather than share a module across the boundary.

**Gate:** `scripts/gates/domain_boundary.py`, over the census in `scripts/domain-boundaries.json`. Landed green as a ratchet, with one crate edge and eight `ui/src` edges grandfathered, each carrying the issue that removes it.

**Why:** [`composability`](composability.md) already says most features are removable blocks over always-on substrate, and it had no gate. Without one the claim decayed in the direction every codebase decays: a feature needed something a neighbour had, imported it, and two features that were never related began failing together. The cost is not theoretical — the feature-independence audit found four unreported bugs of exactly this shape, including an evicted tab freezing other notes' dataview queries and a cancelled scan killing live updates for the rest of the session. The gate is deliberately about **edges, not sizes**: a wide module is not a violation, and a module that makes an unrelated feature's failure your failure is. Size is [`component-composition`](component-composition.md)'s question, and answering it here would have meant splitting files that are wide because they are chokepoints on purpose.

The idea has names elsewhere, and they are worth knowing because each carries its own literature: **bounded contexts** (domain-driven design — a model is only consistent inside its boundary, and two contexts translate rather than share), **vertical slices** (a feature owns its whole stack rather than borrowing layers from neighbours), and Sandi Metz's *duplication is far cheaper than the wrong abstraction* — the reason the next paragraph prefers two copies to one shared module. DRY is about knowledge, not about lines of code: two blocks whose code happens to match today are two owners of two facts that will diverge, and joining them couples their release, failure and removal.

The rule that duplication beats a cross-domain import is narrower than it sounds, and the narrowing is load-bearing. It governs **runtime** dependencies, because those are what make two features fail together. It says nothing about build-time sharing: the design system is a component library the shipped app does not contain, so no amount of sharing there can couple two features at runtime — [`design-system`](design-system.md) stands unchanged, and so does [`single-owner-facts`](single-owner-facts.md), which governs documentation. Nor does it license duplicating a **write path**: two copies of one upsert is how the watcher silently stopped writing `type_id`, and collapsing that duplication is what found the bug. Duplicate a pure function across a boundary; never duplicate the code that owns a row.

When substrate has to tell a block that something happened, it does not call the block. It reports through a trait it owns, and the shell passes in the block's implementation: the scan reports each file to a `ScanSink`, the watcher and rename report each change to a `ChangeSink`, and search implements both. The substrate then builds, runs and tests with no block present, and a new listener joins by writing an implementation, not by editing the substrate. Assembling one vault's blocks is the shell's job too, which is why `open_vault` lives in the engine's `compose` module and not among the substrate commands.

The same goes for a block that genuinely needs another block — equations evaluating a property that property references resolve. It declares the need in the plugin registry (`requires`), so the toggle refuses the broken combination, and it receives the behaviour through a slot owned by substrate (here the editor core's `propertySlot.ts`), which the shell fills. It never imports the other block. The editor core itself is substrate: the editor cannot be switched off. The features rendered inside it are blocks, so one directory holds several domains, and the census names them by path prefix.

**Exceptions:** The shell is exempt by definition — `cubical-engine`, `cubical-ipc`, `cubical-app`, `cubical-cli`, `App.tsx`, `main.tsx` and `ui/src/shell/` exist to wire blocks together, and keeping that set small is the point. `ui/src/shell/` is where composition goes when doing it in `App.tsx` would grow the shell's budget, or has to happen before `App` exists: it plugs one block's renderer into another's seam and hands each block's settings contribution to the substrate that renders it. It holds wiring only and grows no feature logic. Test code is exempt: `#[cfg(test)]` modules and `.test.` files may reach anywhere. An unclassified `ui/src` directory defaults to **block**, so a new feature is fenced in from its first commit rather than after someone notices. Everything else is a grandfathered entry with an issue number, and an entry without one is not an exception, it is an unrecorded violation.

**Detail:** `scripts/domain-boundaries.json` is the census and the paydown list · [`composability`](composability.md) owns the substrate-versus-block distinction itself · [`crate-separation`](crate-separation.md) is the other half of the layering, answering "may this layer call down to that one" where this gate answers "may these two features know about each other at all".
